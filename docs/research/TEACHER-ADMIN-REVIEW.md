# 教師管理頁審查報告

> 日期：2026-11-18　對象：`teacher.html`＋`teacher/`（v3.14.0，分支 `claude/gracious-pasteur-773n2t`）
> 立場：資深遊戲營運／遊戲 UX，同時站在國小電腦課老師的角度。**只審查，沒有改任何程式。**
> 對照文件：[`SPEC-TEACHER-ADMIN.md`](../SPEC-TEACHER-ADMIN.md) §2～§7、§13；[`GAME-DESIGN-REFS.md`](GAME-DESIGN-REFS.md)；[`LAUNCH-TEACHER.md`](../LAUNCH-TEACHER.md)。

## 0. 怎麼審的（和限制）

- **實際操作**：起 `python3 -m http.server 8765`，用 `tools/browser-test/mock/` 的假 Firebase（開 `__RULES`）、Playwright（Chromium）登入教師頁，種了 3 個班、31 份存檔、6 則回報、5 則回饋、1 個換名紀錄、1 個進行中活動、1 個已結束的排行榜；8 個分頁各截桌機 1280 與手機 390，再把 5 個常見任務各走一遍並數操作次數。
- **跑過既有測試**：`t1.test.js` 157 項、`t2.test.js` 158 項，全過（沒有失敗）。
- **規則**：用 `tools/rules-test/` 已有的 Firebase 模擬器，另外寫了一份**用完就刪**的小測試（沒有進 repo）：老師的 20／200／400 筆批次寫入、老師的「回報＋抓蟲榜＋信＋紀錄」混合批次，都**通過**；也確認學生匿名帳號讀得到整個 `mg_scores` 與整個 `mg_bugboard`。
- **注音輸入法**：用 Chrome DevTools Protocol 的 `Input.imeSetComposition` 模擬，不是真的用輸入法打字，但行為一致。
- **做不到的**：沒有連真的 Firebase（雲端環境連不到）、沒有真學生、沒有投影機實測。「操作要幾秒」是經驗估計。
- 標記：**（實測）**＝我在這次跑出來的；**（讀程式）**＝只看程式推得；**（經驗判斷）**＝研究資料沒涵蓋。研究資料本身的查證程度見 `GAME-DESIGN-REFS.md` 開頭（多數沒讀全文）。

## 1. 總評

**做得很完整，而且防呆比一般自製後台好很多。** 規格 §2～§7 的條目幾乎全部做到（缺的只有規格自己排到第二版的東西，見 §5）；發獎「先快照、固定信件 ID、最後才寫 `awarded`」、回報審核「同一個 batch 寫三樣、分數從 reports 重算」、送出前一律有「學生會看到的樣子」＋一行摘要、老師頁用具名 app 不影響學生機，這幾個地方的設計比我看過的多數校內後台都扎實。重複發獎我找不到會真的發生兩次的路徑；跟 `firestore-rules.txt` 也沒有衝突。

**真正的風險不在「少功能」，而在「上課現場的順手度」與幾個資料細節：**

1. **老師打的自由文字會進到全校學生讀得到的文件**（抓蟲加分理由、回報回覆、名字沒問題的真名）。這是這份審查裡最需要先處理的一項。
2. **中文搜尋在注音輸入法下壞掉**（學生頁、信箱頁的搜尋框），這是老師每天會碰到的第一個動作。
3. **「上課中要看誰卡住」這件事教師頁幾乎沒回答**：只有「今天有存檔」的絕對時間，沒有「現在在線」、沒有卡關訊號；總覽「今天上線」卡片點進去是**全部 31 人沒篩選**（實測）。
4. 幾個**會讓老師心裡不安的小地方**：信箱預設收件人是「全校」、活動重複開沒有提醒、已結束沒發獎的排行榜沒人提醒、發獎視窗點背景就整個消失。
5. 手機：回報審核可以用，但活動列表、抓蟲榜、寄出紀錄的**操作按鈕在畫面右邊被切掉**（實測，見截圖）。

一節 40 分鐘的課，5 個常見任務全部做完只要約 **50 次操作**（約 5～8 分鐘，經驗判斷），時間夠；比較吃力的只有「手動加分 3 位同學」（19 次操作）。

## 2. 必改（建議上線前處理）

### M1　老師打的自由文字與真名，寫進了學生讀得到的 `mg_bugboard`
- **位置**：`teacher/tab-bugs.js:222`（`notes[].why`）、`:85`／`:127`（`reports[].reply`）；`teacher/tab-students.js:150`（`nameOk: s.name`）；規格 §1.5、§7.1、§7.3。
- **問題**：
  - 「手動加分」**強迫老師寫理由**（`:216`），理由原文存進 `mg_bugboard/{id}.notes[]`。老師很自然會寫「小明在下課時口頭回報」「幫 5 號找到 bug」。
  - `mg_bugboard` 規則是「登入者都能讀」。實測（規則模擬器）：學生匿名帳號 `getDocs(collection('mg_bugboard'))` 讀得到 `nameOk` 和 `notes[].why`。學生端抓蟲榜本來就會讀這個集合的前 10 份（`nw-notice.js:69`）。
  - `nameOk` 存的是**真名**；但 `nw-notice.js:5` 的註解與規格 §7.3 都寫「`mg_bugboard` 也不存真名」。**規格 §1.5 與 §7.3 自己互相矛盾**，程式照 §1.5 做了。
  - 回覆 `reply` 是要給本人看的，但也一樣被別人讀得到。
- **為什麼**：任務要求第 4 點（真名不能露給別的學生）；規格 §1.3 把 `mg_nw_flags` 設成「只有老師能讀」就是為了這件事，抓蟲榜這邊漏了。老師打的字不是下拉選單，風險是人為的、不是技術的。（讀程式＋實測規則）
- **具體改法**：
  1. `notes[]` 只存 `{ pts, t }`，理由只寫進 `mg_admin_log`（老師專用）。要在教師頁看明細，就從 log 對照。
  2. `nameOk` 改存**正規化後名字的雜湊**（學生端 `newworld.js:173–176` 的 `checkName` 同樣先雜湊再比）；或搬到 teacher-only 集合 `mg_roster/{id}`，學生端改讀自己那份 `name0`＋一個 `nameOkHash`。
  3. `reply` 的輸入框下加一行固定提示「這句話其他同學也看得到，不要寫姓名」。
  4. 一次搬移（§1.8）要同步把已寫進去的舊 `notes[].why`、`nameOk` 清掉。
- **工**：中（半天～1 天，含學生端比對改動、補測試）。只做第 1、3 點是**小**。

### M2　中文搜尋框在注音輸入法下壞掉
- **位置**：`teacher/tab-students.js:68`、`teacher/tab-mail.js:88`。
- **問題**：每次 `input` 事件都**整個重畫並換掉輸入框**，沒有 `isComposing` 保護。實測（CDP 模擬注音）：打「ㄒㄇ」時輸入框已被換成新元素，最後輸入框內容變成 `ㄒㄒㄇ小明`、列表 0 筆。老師用姓名找人是最常見的動作。
- **為什麼**：（實測）；Hodent 的認知負荷原則（`GAME-DESIGN-REFS.md` §4.1）——第一個動作就失敗，後面都不會信任這個工具。
- **具體改法**：搜尋框只更新 `<tbody>`／候選清單，不重畫輸入框；`input` 處理加 `if (e.isComposing) return`，改在 `compositionend` 觸發一次。
- **工**：小（1～2 小時，兩處）。

### M3　信箱預設收件人是「全校」，而且「全校＋禮物」沒有加重確認、也不提醒重複寄
- **位置**：`teacher/tab-mail.js:22`（沒有帶參數進來時 `mode` 預設 `'all'`）、`:117–131`（`send()`）。
- **問題**：
  - 老師從左邊分頁點進信箱，收件人預設選好「全校」。只填標題、按「預覽並寄出」再按「確認寄出」就寄給全校。預覽有寫「寄給 全校 31 人」，但這是老師最容易手滑的一個。
  - `收回`不會扣回已領的東西（畫面有寫清楚，這點做得好），所以全校誤寄武器、改名卡是**無法補救**的。
  - 沒有「這個標題最近 7 天已經寄給重疊對象了」的提醒；手動信是自動 ID，同一份禮物寄兩次就是兩封（學生領兩次）。
- **為什麼**：任務要求第 4 點「會不會重複發獎」；研究資料 §12 引用的原神、Warframe 重複發獎事故都是人為重送。防呆分級（經驗判斷）：越不可逆、影響越大，確認越重。
- **具體改法**：
  1. 預設不選任何收件人（或預設「學生」），按寄出前要選。
  2. 收件人是「全校」或超過 60 人、而且有禮物時：確認視窗多一個勾選「我確認要寄給全校 N 人，寄出後無法收回已領的東西」才亮「確認寄出」。
  3. 寄出前比對最近 7 天的 `mg_mail`：標題相同且收件人有重疊，就在預覽上方顯示黃色提醒「7 天內你已經寄過同標題的信給其中 N 人」。
- **工**：小～中（半天）。

### M4　「發獎」與「手動加分」視窗：點背景或按 Esc 會丟掉所有已填的內容
- **位置**：`teacher/util.js:41`（Esc）、`:43`（點背景）。
- **問題**：`modal()` 一律「點旁邊或 Esc 就取消」。這對「確定嗎？」類視窗很好，但發獎視窗要勾人、設三級獎品、參加獎，是整個頁面**最費工的表單**；手機上滑動時手指點到視窗外就全沒了（實測：加分視窗點背景即關閉）。
- **為什麼**：防呆與可逆（`GAME-DESIGN-REFS.md` 沒有專節，**（經驗判斷）**：表單型視窗點背景不應關閉）。
- **具體改法**：`modal()` 加 `sticky: true`：點背景不關、Esc 先問「放棄已填的內容？」；發獎、手動加分、確認回報（有回覆欄）、學生卡的操作都設成 sticky。
- **工**：小（1～2 小時）。

### M5　「作廢名次快照重做」的警告說「還沒寄出任何信，所以安全」，但這句話在最需要它的時候是錯的
- **位置**：`teacher/tab-events.js:328`（說明文字）、`:244`（只有「有快照且還沒 awarded」才出現這個按鈕）。
- **問題**：這顆按鈕只在**發獎做到一半失敗**（快照寫了、信寄了一部分、`awarded` 還是 false）時才會出現——也就是**可能已經寄出信**的時候。作廢後重做，名次可能變，`ev_{ID}_{pos}` 這種固定 ID 會被**覆蓋成給別人的信**；已經領走的人保留獎品、新的第 N 名又再拿一份。
- **為什麼**：任務要求第 4 點（重複發獎、誤操作毀資料）。程式裡的註解（`:386–396`）說明了「重寄會照同一份快照」這個保證，**但作廢重做正好繞過它**。（讀程式）
- **具體改法**：作廢前先 `getDocs(where documentId prefix 'ev_{ID}_')` 數一下已存在的信；有就拒絕作廢，只留「照快照繼續寄」；或把確認文字改成「已經有 N 封信寄出，作廢後這些信可能被覆蓋」並要再按一次。
- **工**：小（1～2 小時，含測試）。

### M6　已結束但還沒發獎的活動排行榜，沒有任何地方提醒老師
- **位置**：`teacher/tab-overview.js`（沒有這張卡）、`teacher/tab-events.js:141`（列表只標「已發獎」，沒標「待發獎」）。
- **問題**：學生端結束後的活動卡寫「老師可能會寄獎品到信箱喔」（規格 §9.1），這等於**對孩子的承諾**。但教師頁沒有任何「待發獎」提示；老師若忘了，只有學生會一直等。
- **為什麼**：研究 §2.1 兒童保護與 §4.5：「不做只有這次拿得到」與「老師會補發」是成立的前提；承諾不兌現是對孩子的信任傷害。**（經驗判斷）**：營運後台最重要的就是「待辦」被看見。
- **具體改法**：
  1. 總覽加一張「待發獎」卡（紅數字＝要動作）；點進去直接開那個活動的詳細頁。
  2. 活動列表「已結束」區對 `ranking` 且 `!awarded` 的列加黃色 chip「待發獎」並排最前。
  3. 同時給 `hunt`／`classwar` 結束的不必處理，不要加噪音。
- **工**：小（半天）。

## 3. 建議（體驗與效率；越前面越值）

### S1　上課中「誰卡住了」：學生頁沒有答案　★建議前 5
- **位置**：`teacher/tab-overview.js:22`、`teacher/tab-students.js`（欄位 `COLS`、`:34`）。
- **問題**（全部實測）：
  - 總覽「今天上線 24」卡片 `data-go="students"` **沒帶任何篩選**，點進去是全部 31 人。
  - 「最後上線」顯示 `11/18 05:06` 這種絕對時間，沒有「3 分鐘前」；也沒有「現在在線（10 分鐘內有存檔）」的篩選。
  - 一個班 28 人，老師站在教室中間想知道：誰還沒登入、誰連敗、誰卡在第一個任務。表格有 11 欄，但沒有「任務進度」、「連敗」、「這節課打了幾場」，要一個一個點開學生卡才看得到任務。
- **為什麼**：資訊層級（`GAME-DESIGN-REFS.md` §3.1 Bycer：先想使用者此刻要找什麼資訊）；Gee 的「令人愉快的挫折」（§1.1）——老師要能看出誰從愉快變成純挫折。**（經驗判斷）**：課堂是即時場景，要求「5 秒內看出一個班的狀態」。
- **具體改法**：
  1. 學生頁頂端加「班級快覽」：選一個班後出現一條摘要「在線 20／28、還沒登入 5、沒進新世界 3、連敗 ≥3 場 2 人」，每項可點成篩選。
  2. 「最後上線」改成相對時間（hover 才是日期），並多一個「現在在線」篩選。
  3. 表格加「任務」「這節課場次」兩欄（資料已經在 `nw.quest`、`nw.stat`）。
  4. 總覽卡片「今天上線」、「新世界玩家」要帶篩選參數（`played` 已經有；補 `today`）。
- **工**：中（1～1.5 天）。

### S2　手動加分：一次只能一個人、搜尋認不得「503 5」、視窗細節　★建議前 5
- **位置**：`teacher/tab-bugs.js:193–227`。
- **問題**（實測）：
  - 「幫 3 位同學補分」= **19 次操作**（切分頁 1＋每人 6：開視窗、打搜尋字、選人、分數、理由、送出）。三個人理由往往一樣。
  - 搜尋字串是 `名字 暱稱 座號 班級短碼` 用空格連起來比對，所以「503 5」**找不到（0 筆）**；「5」出現 24 筆。老師最自然的說法「504 的 5 號」做不到。
  - 學生頁的搜尋（`tab-students.js:34`）同一個邏輯，「503 5」也找不到（讀程式）。
  - 只列已有存檔的學生；從沒進過遊戲的人無法補。
  - 「分數」輸入框的提示文字「例 2 或 -1」被截斷成「例 2 或」（截圖 `audit-d1280-bonus-modal.png`）。
  - 加分後學生沒有收到任何通知（只有榜上數字變）。
- **為什麼**：「一節課 40 分鐘」；任務 2.4 的任務之一就是這個（SPEC §7.1 專門寫了「504 的 5、12、1 號」）。
- **具體改法**：
  1. 搜尋支援「503 5」「5號」「503」；把每個詞拆開、全部符合就算（AND）。
  2. 選人改成可多選（勾選清單＋已選晶片），同一個分數與理由套用到所有人；一個 batch 寫完。
  3. 加分視窗底部加選項「同時寄一封感謝信」（預設勾，固定 ID `bonus_{id}_{t}`）。
  4. 修輸入框寬度。
- **工**：中（1 天）。做完 3 位同學約 7 次操作。

### S3　活動表單：切類型殘留標題、重複開沒提醒、範本藏在類型底下　★建議前 5
- **位置**：`teacher/tab-events.js:254–256`（切類型時 `keep` 保留 title／desc）、`:268`（新增預設是「限時加倍」＋第一個範本）、`save()`（沒有重疊檢查）。
- **問題**（實測）：
  - 預設進來是「限時加倍」，範本「咕咕鳥大量出沒」在「限時討伐」底下。老師要先猜到類型，才找得到範本；點了「限時討伐」後，**標題仍是「本週經驗加倍」、說明仍是「這個星期打贏魔物，獵人經驗變 2 倍！」**，如果沒再選範本，直接送出就是標題與內容對不起來的活動。
  - 已經有一個進行中的「咕咕鳥大量出沒」時，再建同款**完全沒提醒**，結果同時有兩個一模一樣的活動（`hu1` 與 `hunt_coo_1118`），兩個都會給 100 字元。
  - 「活動 ID」與提示「學生存檔要用它當欄位名稱」是工程師用語，老師不需要看到。
  - 「再開一次」對 `hunt` 活動，已經達標領過獎的人**會再領一次**（新 ID），畫面沒說。
- **為什麼**：防呆；任務要求第 4 點（重複發獎）。**（經驗判斷）**：老師的心智模型是「我要開咕咕鳥活動」，不是「我要選一個類型」。
- **具體改法**：
  1. 活動頁頂端改成「用範本開活動」大按鈕列（6 個範本直接列出）＋「自訂」；預設不要預填範本。
  2. 切類型時清掉 title／desc（或問一下）。

## 7. 安全與資料

### 7.1 真名會不會露給別的學生？
| 文件 | 學生讀得到？ | 內容 | 結論 |
|---|---|---|---|
| `mg_bugboard/{id}` | 是 | `nameOk`＝**真名**；`notes[].why`＝老師打的自由文字；`reports[].reply` | **M1** |
| `mg_scores/{id}` | 是（整份） | `name`＝真名（舊站就有） | 既有限制，L1 |
| `mg_events/{id}.result` | 是 | 只有 `班級_座號`、暱稱、分數、場次（`ev-calc.js` `buildSnapshot`） | ✅ 沒有真名 |
| `mg_mail/*` | 是 | 標題、本文、`aud: id:班級_座號`；系統信本文不含名字 | ✅（`aud` 會讓人知道「誰收到了什麼」，無法避免） |
| `mg_news`、`mg_events` 其餘欄位 | 是 | 老師自己打的標題與說明 | 老師打字，要提醒（同 M1 第 3 點） |
| `mg_nw_flags` | **否**（只有老師） | 真名、回報內容 | ✅ |
| `mg_admin_log` | **否**（只有老師） | 真名、操作摘要 | ✅ |

### 7.2 老師誤操作會不會毀資料？能不能復原？
- 教師頁**沒有**任何「刪除學生存檔」「改學生字元／裝備」的功能，這是好的設計（給東西一律寄信）。
- 有確認視窗的：收回信、刪除活動、刪除公告、提早結束、不採用、撤銷確認、隱藏暱稱、名字沒問題、執行搬移。
- 可逆：撤銷確認（分數重算）、手動加分（負數）、延長結束時間、提早結束後可再延長、公告可重貼、搬移可重按。
- **不可逆**（畫面都有寫清楚）：已領的信收回不扣回、撤銷確認不收回已寄的信。
- **不夠**：全校誤寄（M3）、表單視窗誤關（M4）、作廢快照（M5）、「名字沒問題」沒有重新鎖定（S12 j）、刪除活動不顯示參加人數（S12 b）。

### 7.3 會不會重複發獎？
- 回報確認：`already` 檢查＋`mailExists('bug_{flagID}')`＋同一個 batch；實測重按只補寫狀態。✅
- 活動發獎：固定 ID `ev_{ID}_{pos}`／`ev_{ID}_p_{學生}`；中途失敗再按會照同一份快照。✅（唯一例外是 M5「作廢快照」）
- 一次搬移：固定 ID＋`mailIds` 比對。✅
- 手動寄信：自動 ID，**會重複**，無提醒（M3）。
- 限時討伐／班級挑戰獎勵：學生端 `NW.ev[ID].done`／`NW.evDone` 擋重複；「再開一次」是新 ID，會再領（S3，是設計，但要說清楚）。

### 7.4 跟 `firestore-rules.txt` 有沒有衝突？
**沒有。** 教師頁所有寫入（`mg_mail`、`mg_events`、`mg_news`、`mg_bugboard`、`mg_config/class_sizes`、`mg_nw_flags` merge、`mg_admin_log` create）都是 `isTeacher()` 允許的；讀取 `mg_scores`、`mg_nw_flags`、`mg_admin_log` 也允許。`tools/rules-test/` 沒有涵蓋「多筆批次」，我用模擬器補驗：老師 400 筆 `mg_mail` 批次、回報／抓蟲榜／信／紀錄混合批次都通過（建議把這兩條補進 `rules.test.mjs`，小）。學生端能讀 `mg_bugboard` 的 `nameOk`／`notes` 是**規則允許、但內容不該放**，不是衝突（M1）。
